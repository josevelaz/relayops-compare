Audit of both agents

Two OpenCode sessions received the same RelayOps brief at the same time. They could not share files. This page records what each session produced, how long it ran, and where it fell short.

Sessions

Both agents received the same prompt at 12:42:35 on 8 September 2026. Muse Spark declared the product complete at 13:38. Astra kept building until 14:43. Spark finished about 1 hour 5 minutes earlier.

“Declared complete” is the first wrap-up message after the original prompt. Spark then sat idle until 14:23, when a second prompt asked it to build production. Both sessions later received OpenCode restart noise around 15:14. Token counts include that extra activity. Source lines count TypeScript, TSX, and CSS under each app’s src/.

What both got right

  • Every required navigation area exists: Overview, Incidents, Alerts, Services, Deployments, On-call, Analytics, Postmortems, Teams, Settings.
  • StyleX is the styling system. Neither used Tailwind or a prebuilt component kit.
  • Seeded data is internally consistent. INC-1042, Payment Gateway, Sarah Chen, and the rollback of payment-gateway@4.18.2 appear in incidents, services, alerts, and deployments.
  • INC-1042 is a working incident workspace: status, timeline, responders, tasks, related alerts, related deploys, and customer updates.
  • Payment Gateway and the Payments team have detail views.
  • Postmortems can be opened and edited. Users can create an incident from the UI.
  • Search and filters change visible results. Dialogs open and close.
  • Each session ran a reviewer subagent near the end. Neither of these two sessions called the UI designer.

Astra — where it succeeded

  • Higher information density. The overview reads as an operations console, not a grid of stat cards.
  • State persists in localStorage (relayops-astra-v1). Reloads keep created incidents and edits.
  • Incident, alert, and settings screens go deeper: bulk alert ack, CSV export, incident configuration, member invite.
  • Accessibility work is visible: labeled dialogs, aria-current on nav, chart aria-labels, skip and focus handling.
  • Fewer tokens than Spark for more source. The session was denser, but it took much longer.

Astra — where it failed

  • Routing is a catch-all /$ page that splits pathname. It works, but it is not file-based TanStack routing. Deep links are not first-class routes.
  • Several files are too large for the brief’s maintainability bar: Incidents.tsx (~1,510 lines), data.ts (~1,305), ui.tsx (~1,199).
  • The local machine accumulated a Playwright browser cache (~1 GB) during the session. That is not in git, but it is leftover process waste.

Spark — where it succeeded

  • File-based routes for list and detail pages (/incidents/$incidentId, /services/$serviceId, and the rest). This matches TanStack Start practice.
  • A smaller, clearer module split: tokens, model, store, shell, command palette, create-incident modal.
  • Keyboard use is explicit: ⌘K search, C create incident, / search.
  • The incident workspace is easy to scan: status and severity controls, timeline, tasks, and customer/internal comms on one screen.
  • The data model is one file of related records, so service health, alerts, and deploys stay aligned.

Spark — where it failed

  • No persistence. Incident creates, acks, and edits reset on reload.
  • Incident notes always post as Sarah Chen, not as the signed-in user.
  • @stylexjs/unplugin peers conflict with TanStack’s unplugin 3. GitHub Pages npm ci failed until legacy-peer-deps was added.
  • The StyleX Vite plugin is constructed with dev: true even for production builds.
  • Index routes use trailing slashes (/alerts/). That is valid, but it is a sharp edge for links and GitHub Pages.
  • The full session still used far more input tokens (about 3.4× Astra) and more assistant messages to ship about half the source lines. Context use was inefficient even though it finished first.

Judgment

Spark shipped a complete product in 56 minutes. Astra needed 2 hours 1 minute. Astra spent tokens more carefully and built a denser, persistent workspace, at the cost of time, a catch-all router, and oversized files. Spark was faster and produced a cleaner route tree, at the cost of no persistence, a dependency conflict, and much higher token burn per line of code.
